# Private QQ Native source export

`createQQMemoryBridge(...).exportNativeSources(key)` is an asynchronous in-process Bridge API for a future Host composition. It requires an existing private active V2 `prepareReply` packet and a still-valid issued prepared handle; role, routing generation and active packet are checked before and after Host validation and after reading. It does not export or transfer the handle, rendered reply or a provider capability.

Successful output is `{ok:true,authority:'requires-kernel-binding',packet:{character:{id,epoch},conversationKey,sources:[{sourceFacts,events,eventRefs}]}}`. It is a detached copy of the exact selected current source and up to six authorized prior sources. Its contents are original durable spool events rather than rendered chat text. Capture still does not prove Source ACL, Native admission or provider safety: a future trusted Host must independently resolve and bind every source through the kernel before dispatch. V1 remains the default; this API does not change routing, permissions, activation or network behavior.

At export the Bridge rereads each complete committed segment, requires the stored cursor to cover its exact current byte length, verifies the complete ordered parts and each original event reference, source role/epoch/conversation/actor/producer/segment/delivery scope, and checks the reassembled source digest. Missing, extra, duplicate, changed, stale, unprepared, retired or invalid material returns structured `{ok:false,code,error,hint}` with no partial packet. At most seven sources, 128 event references and 2 MiB of serialized sources are exported; oversize is rejected, never truncated. The cache, durable spools and caller-visible objects are not shared by reference.

The tests use synthetic temporary spools and a fake Host client. They validate Bridge integrity and packet compatibility; they do not establish real QQ source identity, Host ACL, Native middleware or provider execution. Physical external file races and Host identity changes beyond the existing role/routing/prepared checks remain the responsibility of the future integration and its fenced authority checks.
