# QQ 过期交互编号误入模型（2026-11-07）

## 完整逻辑

1. **链路**：QQ 入站由 bridge 的 `handleIncoming` 查会话 pending；严格编号模式中，远端取消、过期或结束会移除 pending。此后到达的旧编号回复以前继续走普通聊天并调用模型。
2. **机制**：已实测的官方审批在 90 秒后取消，后到的带编号拒绝因没有 pending 被当作新聊天。现在只在 `interaction.requireRequestId=true` 且无 pending 时识别明确的审批动词加八位十六进制编号，或八位编号加提问答案；直接回复「该编号已结束或不存在，请等待新请求」，不进聊天、记忆或模型。当前 pending 的原身份、正确/错误编号处理不变；旧模式默认 false 保持普通聊天兼容。
3. **影响面**：仅 QQ 严格编号模式的无 pending 交互格式；普通聊天不变。该格式会触发一次 QQ 提示，但不产生模型请求；用户真实消息、私有账户和配置未被本次夹具读取。
4. **取舍**：进程内过期编号表误拦较少，但重启和不认识的编号无法覆盖；选择语法识别覆盖过期、远端取消和未知编号，代价是严格模式里 `8位hex 空格 内容` 的普通聊天也会被识别为交互。缺省旧模式无此改变。
5. **生效**：更新对应安装后重启 QQ 桥接；严格模式需原有 `interaction.requireRequestId=true`。没有修改官方 App、账号或真实 profile。
6. **验证**：实际 bridge VM 与 pumpMux 夹具、官方 Node24、临时 HOME/DSH_HOME、sandbox 禁非回环。`_backups/20261107-qq-expired-interaction/red.log` 显示无 pending 和远端取消后均错误地调用一次 prompt（预期零），exit 1；`checks.log` 的定向交互、桥接、提问、协议和 regressions 五项均 exit 0，验证零 prompt/可见提示、旧模式与正常聊天兼容、活跃错误编号不消费、正确编号成功、原交互安全回归。全 audit 与插件组合由主线执行；真实 App 与 QQ 的复验须按授权执行。
7. **回滚与残余**：旧独立树文件在 `_backups/20261107-qq-expired-interaction/` 保存；回滚前备份并重启桥接，保留全部用户状态。严格语法不可区分刻意使用相同格式的普通聊天；初始夹具未覆盖真实 QQ 端；主线已补迟答复验，系统重连的其它情况仍未验。没有追溯删除原有模型会话或消息。

## 两条路径

- pending 存在：沿用原始身份与编号检查，仅当前编号能够回传 DSH。
- pending 不存在且严格模式：匹配交互语法则提示编号无效并停止；非匹配文本继续正常聊天。
