# 人格编辑 API：绑定角色与 epoch

## 现象与根因

切换到新角色后，旧页面草稿可能仍属于前一个角色。旧保存请求不带角色身份，服务端在收到请求时解析当前角色路径，因而可能把旧草稿写入新角色。此案例涉及人格用户数据；本次使用隔离 HTTP 夹具验证，未在真实用户角色上写入。

## 完整逻辑

1. **链路**：插件 Host 的 `/dsh-surfcore/api/persona` GET 返回角色身份及该角色人格层；POST 接受核心、语气、日常、场景及备份恢复，写入角色文件并触及角色清单。
2. **机制**：GET 在同一同步段捕获 `{id,epoch}` 并按其生成各层路径；POST 完整读取 body 后捕获当前角色，在任何备份、复制或写入前校验可选 `expectedCharacter`。提供字段但格式错误、角色不同或 epoch 已变化，返回 HTTP 409 与 `PERSONA_CHARACTER_STALE`、错误和操作提示。旧客户端不传字段维持原行为；无角色时 GET 返回 `character:null`，旧布局仍可使用不带身份字段的保存。
3. **爆炸半径**：Host 及所有人格 API 调用者均可能受影响；错误写入会污染另一角色的人格文件和备份。新增守卫只约束显式携带身份的请求，未修改现有用户数据或凭据。
4. **取舍**：方案 A 前端重挂载可以减少旧草稿，却无法阻止延迟请求；方案 B 后端同时绑定角色和 epoch 可在写入前拒绝过期请求，新增可选字段以兼容旧客户端。选择 B，并配合前端携带该字段；没有字段的旧客户端仍不受此保护。
5. **生效**：须在组合候选中合并对应前端和后端，重新加载插件宿主。此会话没有重载真实 DSH。
6. **验证**：隔离目录复制当前 Host 代码并启动本机回环 HTTP 夹具，验证 GET 两角色及无角色身份、A 正确保存、切 B 后 A 的四层写入与恢复全部 409、错误身份/同角色旧 epoch 409、A/B 文件和备份逐字不变、B 正确保存与恢复、旧客户端及无角色旧布局保存、一般 I/O 失败 code/hint。另在 HTTP body 首段被 Host 接收后切角色，再发完 body，确认 409 且无写入。命令与日志见交接。
7. **回滚与残余**：旧 index 副本在 `_backups/20261106-persona-api-epoch/`；回退前应停止宿主并保留角色与备份文件。无身份字段的旧客户端仍按原路径保存；Node 同步段外的独立进程写入未作为跨进程锁证明；真实 App 页面交互和组合门禁须由主会话验证。
