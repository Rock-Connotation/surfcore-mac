# QQ 严格编号回答提示避免照抄占位词

## 现象、根因与完整逻辑

1. 链路：DSH question/requested → bridge.pumpMux → pending登记 → QQ通知 → handleIncoming/handlePendingAnswer → buildQuestionAnswers → 官方respond。下游按完整选项label匹配，提示只影响严格编号模式；普通模式兼容。
2. 机制：旧通知把“请求编号 答案”放在可复制引号内。既有真实验收两次发送字面“编号 答案”，selected为空且custom有原文，不能算精确选项成功。根因是提示把占位词表现成了答案，不是回答编码契约错误。现改为先写实际编号，空格后写完整选项文字或自己的回答，并明确不要照抄“答案”。
3. 影响面：桥接进程、QQ通知读者、官方答案消费者；只改提示字符串，不改变选项编码、主人鉴权、pending生命周期、旧默认false或模型调度；不增外发/费用。
4. 取舍：A把占位词“答案”作为默认选项解析会改变语义且可能代用户选择；B只消除提示歧义并验证真实完整label路径，成本一行文案和消息链路用例，回滚清晰。选B。
5. 生效：安装新候选并重启其QQ桥接后，新提问通知使用新提示。当前已安装的抖音UI候选803b647未包含本提示，不能用它证明新QQ实机通过。
6. 验证：`node scripts/test-qq-interactions.mjs`先红：实际通知为“回复编号 答案”，未命中“完整选项文字”；修正后exit0。用例经过真实mux与handleIncoming，按实际requestId发送A，官方answers.selected严格为['A']，保留主人来源、普通模型prompt计数为0。原始red/green日志在本轮私有证据目录；组合门禁由主线最终候选重跑。尚无新增QQ真实消息/模型调用。
7. 回滚与残余：按明确路径还原前一候选；原始文件副本保存在_backups/20261107-readiness，保留所有角色/账本/会话。真实手机精确选项与睡眠/连续在线仍待独立授权及补验，不把本夹具算实机通过。

## 失败路径

现有错误编号、过期编号、非主人、未知回执继续走原失败提示，原测试保留；本改动无新增失败分支，无新增接口，不吞旧错误。
