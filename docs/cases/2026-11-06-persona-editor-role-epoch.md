# 角色切换后人格卡编辑器仍显示旧角色

## 现象与环境

官方 macOS App 的隔离验收中新建并加载新角色后，角色页标题已显示新角色及 epoch 2，但等待后人格卡仍显示先前角色的文件路径和草稿。未点击保存，现有角色人格未修改。原始证据在主工作树 `_backups/20261106-macos-wp0/官方App 验收候选/native-ui-role-after-settle.txt`；这不是修复后验收。

## 完整逻辑

1. **链路**：`CharactersTab` 从 `/characters` 取得当前角色，嵌入 `PersonaEditor`；编辑器从 `/persona` 读取层数据，保存各层或恢复备份时分别 POST `/persona`。后端按当前角色定位数据，另由 Host 的角色前置条件护栏完成最终核验。
2. **机制**：原编辑器没有角色 key，`load` 的 effect 只在挂载时执行；切角色只更新外层标题，内部旧角色草稿未重建。原 POST 无身份前置条件，若此时保存，旧草稿可能写入新角色。新编辑器以 id+epoch 为 key，等待 `/persona` 返回相同身份才开放编辑；id 或 epoch 不一致显示错误，清空不可信草稿。每层保存及恢复附带读取到的 `expectedCharacter`，409 时停止后续层写入，展示错误码和下一步。无角色旧布局省略该字段。角色页提供「重新读取角色」按钮：身份变化时重建编辑器，身份不变时保留当前草稿；若仍处于待核对状态，提示用户再点人格卡的「重新读取」并检查。
3. **影响面**：角色页本地编辑和恢复；风险是跨角色覆盖用户人格，非外发或资金操作。角色前置条件由后端在任何写入前校验，单独的前端 key 不构成完整并发保护。
4. **取舍**：只在切换成功时手动刷新改动较少，但跨窗口切角色和切换中请求仍可能错位；选择角色 key 重建、响应身份校验与服务端写入前置条件，代价是一小段身份状态与测试，可避免跨角色写入。已有角色未变的“仅新建、未加载”操作沿用同 key，不清除当前草稿。
5. **生效与重启**：前端与支持身份字段的 Host 护栏需一同进入候选并由官方 App 加载；本子任务未操作 App 或真实角色。旧 Host 无身份字段时，有角色的编辑器保守禁用并提示重新读取，不能依赖旧 Host 进行写入。
6. **验证**：官方 App 内 Node 24.21.0 执行 `node --check plugins/surfcore/lib/client.js` 和 `node plugins/surfcore/scripts/test-client-contract.mjs` 均 exit 0；后者使用真实组件函数和有状态 React 夹具，验证 id/epoch key、旧响应和加载中禁用、切换后空草稿、实际保存四层及恢复所带的 identity、409 后停止后续写入并显示错误、旧无角色语义、create-only 同 key，以及实际点击角色重新读取后身份变化/不变对应的 key 与 busy 闸门。`git diff --check` 通过。
7. **回滚与残余**：文件变更前备份在 `_backups/2026-11-06-perception-ui/client-before-persona.js` 和 `test-before-persona.mjs`；恢复时保留前一批感知 UI 修复。多层保存并非单个原子事务：若切换发生在层与层之间，先前已写的层可能已写入原角色，但后续层会被后端拒绝，不应写入新角色。真实 App 重载与前后端组合验收、完整门禁仍由主会话执行。
