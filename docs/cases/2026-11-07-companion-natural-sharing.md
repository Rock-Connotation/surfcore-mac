## 现象 → 根因 → 影响面 → 修法

## 完整逻辑

1. **链路**：图像点评的 opt-in 六字段结果 → engine 确认 memorySaved → sharing 服务 → 角色内 `douyin/sharing.jsonl`。侧栏模块/日记 → Host 总 API 精确路由 → controller → 角色/epoch 绑定服务。回复 → 全局 engine.lock → 原轮/全局或当日额度持久预留 → HY3 纯文本 adapter → 同角色追加回答。统一观看记忆仍由 Host 原维护者处理。消费者为 engine、Host/controller、日记、侧栏及模型上下文；旧严格 ledger v1/item 格式不扩字段。
2. **机制**：只有真实保存的观看经历才产生开场，不给旧日记补造感受。requestId 在取锁前、后各查一次，避免跨实例重复计费；活请求核对 owner/pid，实际分派前再查角色。取消/晚到结果不退消费，收到的 usage 先持久计入。trusted 人格与字幕/网页/记忆材料分层，聊天不用 agent 工具。当前 epoch 的事件条数作为 revision，所有 GET/POST 快照统一排序；旧响应不能抹掉新回复或 ACK，失效角色与 pagehide 退休在途请求。
3. **爆炸半径**：1 个 Host × 日记/侧栏/API/模型/额度/对话六类读者 × 显式失败 1 = 6。触达付费模型和本机资料，因此采用同源、角色戳、持久预留、幂等、追加写与取消保护；不接平台互动。原始聊天追加保留，页面展示近期 24 条消息/8 条分享，模型取最近 10 条及受众过滤后的统一观看记忆，不宣称聊天偏好全部写入长期记忆卡。
4. **取舍**：A（采用）在现有视觉请求内形成开场，再用轻量本机文本通道接话；收益是真实经历、身份/费用一致，成本是小型 API/存储/UI，回装旧包即可停用。B 让通用 agent 自由开会话或调用工具；入口实现快，但会混用通用模型、权限和账户，回滚牵涉通用会话，风险/长期成本更高。状态排序也比较过纯客户端开始序号：网络先发不代表持久提交先完成，因此采用后端派生 revision，无资料迁移。
5. **生效与重启**：Host/index、engine/model 与 client 需同源安装并重启。最终 f882468 包已先独立重装重启，再装常用并重启；常用现在普通启动。原 13 插件版本、provider/默认模型配置、凭据、人格/立绘均逐项与备份一致。只合并 2 条新 experience、5 条 sharing 事件、已消费额度及生产服务计算的新 token 增量，没有整份覆盖旧记忆卡。旧 inbox 24254 字节及完整归档 49687 字节前缀仍逐字保留。
