## 现象与范围

## 分析与取舍（实施前）

- 链路：Host调度器→feed候选→模型选择→debrief提交Host父作业→共享ASR→模型点评→角色评分→Host记忆；发布另走动态命令与平台回执。
- 机制：旧自由工具回合的提示把深读提交当成完成，且不能硬限模型请求次数；动态命令业务失败仍退出0、缺少记账。评分写盘异常被吞。
- 影响面：Host、CLI、设置页和当前角色账本；涉及模型额度及公开内容，不能让旧巡航、收藏、QQ通知混入单轮。
- 路线A：人工分步调用。成本低、回滚简单，但只能证明各环节，不能证明插件自动等待与自主选择。
- 路线B（采用）：小型Host状态机，复用原feed/debrief/score、B站人格上下文与共享ASR；模型无工具，只能给受限JSON；完成素材后才点评。成本较高，但得到可重复的真实自动链路。独立Astra只读审核支持此路。
- 调度隔离：显式`night.controlledOnly`模式不创建旧生物钟定时器/会话。由运行中的旧巡航切入时须重启后才允许单轮，避免把stop误认为在途动作已消失；单轮结束不自动恢复巡航。
- 边界：初始最多两次模型stream，每次最多2000输出tokens；回忆另计第三次。输入超限拒绝，不静默截断完整转写；不声称金额硬上限或视觉理解。partial/取消/切角色/缺失finish/模型截断均不落评分。
- 真实动态：生成草稿后列出具体账号范围、文字与一次POST，再确认提交。先持久发送意图；业务成功且有效ID才算平台确认；未知结果保留且不自动重发。评论/点赞/转发继续待目标。

## 验证计划

定向状态机、模型终止、身份竞态、账本失败和动态回执行为测试；`npm run test:audit`、`npm run test:regressions`及插件相关测试；组合候选再打包并在官方App独立profile实测。真实调用前核验精确模型路由；发布后独立读回ID、作者和正文，不能只看退出码。
