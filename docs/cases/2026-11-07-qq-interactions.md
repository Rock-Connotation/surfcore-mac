# QQ 审批与提问回执（2026-11-07）

## 完整逻辑

1. **链路**：官方 DSH `$events` waterfall 经 `dsh-client.js` 转成审批/提问帧；bridge 对当前会话登记 pending，再通知 QQ；管理员审批或获许可的提问回答经 `$events/result` 返回。官方 App 打包 `dsh-api-gateway/lib/client.node.js:755` 的取消帧为 `{type:'cancel',eventId}`，由桥接按 eventId 和 clientId 消除匹配 pending。
2. **机制**：旧实现通知发送完才登记，快答可错过 pending；同 eventId 重放会先取消原请求；并发回答和超时存在二次回执风险。现先登记、去重并单飞响应，远端取消清理匹配项。明确结构化拒绝允许在原时限内重试；传输/解析结果未知不重发，提示到 DSH 核对。受控 profile 使用 QQ 配置 `interaction.requireRequestId=true`：审批回复「通过 <8位编号>」或「拒绝 <8位编号>」，提问回复「<8位编号> 答案」；错误/过期编号不能消费当前请求。缺省 false 保留旧裸回复兼容语义。
3. **影响面**：仅 QQ 的 pending/事件桥接及 DSH 回执解释；权限仍按真实管理员身份和提问 owner-only 标记判定，不扩大本机工具权限。发送和模型/外部服务在隔离测试均为桩。
4. **取舍**：保持旧裸回复默认可避免破坏现有用户，但不能阻止旧通知的延迟回复误决新请求；显式编号模式增加输入成本，换取受控常驻验收的请求绑定。去重表每进程最多 10000 项，满时拒绝新请求并提示检查和重启，不静默淘汰历史 ID。
5. **生效**：需集成并重启 QQ 桥接；严格模式需在所选独立 profile 的 QQ 配置显式写入字段。未操作官方 App 或用户配置。
6. **验证**：官方 Node24、临时 HOME/DSH_HOME、sandbox 禁非回环。`scripts/test-qq-interactions.mjs` 红灯 `_backups/20261107-qq-interactions/red2.log`：发送阻塞时 pending 未登记、重复事件产生取消，exit 1。绿色覆盖真实 VM pumpMux、并发回复、过期编号、原角色会话退役、非管理员、明确拒绝/未知、通知失败、官方 cancel 帧和 legacy 裸回复，见 green 日志。原首次红灯因夹具未结束挂起的异步流被中止 exit 130，保留 red.log。相关回归与 audit 的原始日志在同目录。
7. **回滚和残余**：先备份再恢复本批源码并重启桥接，保留用户状态。通知发送失败时 pending 保留到超时，连接类错误可能进入原 outbox，晚到通知在严格编号模式不能误决新请求；旧默认裸回复仍有旧通知串单风险。去重和编号仅限本桥接进程，进程重启后的历史 replay 与迟到旧通知尚未完成持久化去重设计；真实 QQ、官方 App 事件交互和掉线恢复尚未验收。不得用本地 bash/文件工具制造测试审批。

## 两条路径

- 正常：登记当前事件并生成编号 → 通知 → 合法发送者带编号作答 → DSH 明确成功 → 清 pending。
- 异常：重复事件不取消也不重发通知；远端取消或到期只清相应 pending；未知回执不自动重复；严格模式下旧/裸编号不作用于新请求。
