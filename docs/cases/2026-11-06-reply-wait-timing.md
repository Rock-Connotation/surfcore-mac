# 首回复静默窗口测试计时修正

## 现象与根因

组合审计 `test-reply-wait.mjs` 中，消息时间被设为请求前 600ms，静默窗口为 800ms；断言服务端 `waitedMs >= 100`，一次并行编译期间只测得 22ms。`waitedMs` 从桥接 handler 启动时计算，而静默从 `lastIncomingAt` 起算；请求发送、HTTP 处理和调度都可能先消耗剩余的 200ms。该记录证明固定下界不成立，不能单凭它判定产品提前回复。

## 完整逻辑

- **链路**：离线 fixture 启动真实 bridge HTTP handler；`reply` 模式读取最后来信时间并等待剩余静默，返回 `quiet` 和 handler 内 `waitedMs`。
- **机制**：合批、模型读取和请求调度耗时均计入静默窗口，后续新消息重启窗口；等待超时仍受请求的 timeout 限制。测试在服务端 `res.end` 前记录时间，要求该时间距来信至少 800ms；不依赖客户端收到响应的时刻或固定 handler 等待时长。
- **影响**：仅测试夹具和文档；产品代码、真实消息、用户数据、凭据与外部服务均未修改或访问。
- **取舍**：维持固定 `waitedMs` 下界改动最少，但排队导致误报；使用客户端收到响应的时间可能遮掩服务端提前返回。选服务端响应时刻与来信时刻比较，并模拟发送前延迟 300ms；静默期已结束时仍检查没有重新等待一个完整窗口。两种方案的回滚均可通过恢复原测试文件完成。
- **生效**：测试下次运行时生效，不需重启服务。
- **验证**：定向运行 `node --test scripts/test-reply-wait.mjs`；额外边界断言证明 799ms 早返回会失败，800ms 通过。测试连续运行结果及日志见交接。
- **回滚与残余**：原始文件 Git blob `88cdd83c51f74baa7411b61b270ec33289e3fc6c`（修改前与 HEAD 一致）；测试仍运行于真实事件循环，极端调度停顿可能影响原有时限断言。未修改产品行为，未在本任务运行全套审计。
