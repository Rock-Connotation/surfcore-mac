# QQ 桥接启动锁：探测失败与启动窗口

## 完整逻辑

1. **链路**：`src/bridge.js` 在启动早期获取 `state/bridge.lock`，退出时释放；锁格式仍为数字 PID，停止脚本也读取该文件。第二实例读取 PID 后决定是否退出或归档死进程的旧锁。
2. **机制**：原 POSIX shell 把命令不可用转为空输出并误判端口空闲，也把非 LISTEN 连接当监听。即使正确探测空闲，活进程可能尚在启动、还未绑定，因此不能据此偷走它的锁。新 POSIX 路径对存活及 EPERM 保守拒绝；端口检测仅接受有效命令输出及准确 LISTEN 行，未知即占用。确认 PID 不存在的锁通过恢复目录串行归档，核对原 inode 和内容，防止后来者覆盖新锁。
3. **影响面**：同一状态目录的 QQ 桥接启动受影响；双实例可能抢消息并覆盖状态。活 PID 被其他程序复用时会保守阻止启动，需要人工确认；不改账号、发送或用户配置。Windows 沿用原 PID/端口判断及数字锁兼容。
4. **取舍**：路线一保守持有活 PID 并归档死锁；路线二仅依靠端口或进程名识别。前者覆盖启动窗口且不用推断进程身份，但 PID 复用会要求人工检查；后者自动恢复方便，却无法可靠证明尚未监听的进程不是桥接。选前者，变更局限启动锁。
5. **生效**：已运行桥接继续使用已加载代码；新宿主包和下次桥接启动后生效。此分支没有启动或停止任何真实 QQ 进程。
6. **验证**：官方 Node 24 对实际函数的 VM 隔离夹具先红：失败命令误判空闲、ESTABLISHED 误判监听、活进程锁被覆盖；修复后这三项及监听、空输出、端口精确匹配、EPERM、死锁归档、竞争、实际临时回环监听和 Windows 兼容夹具通过。隔离 HOME/DSH_HOME 的 audit 为 164/164、regressions 退出 0（原始日志位于 `_backups/20261107-qq-start-lock/`）；audit 运行期间增强了异常格式拒绝，最终组合需复验。
7. **回滚与残余**：可恢复 `_backups/20261107-qq-start-lock/bridge.js`；旧锁归档保留。恢复目录在异常崩溃后可能残留并阻止接管，须确认无恢复进程后人工检查；无法识别 PID 复用的外部进程。离线夹具不证明真实 App/QQ 启动、收到或发送消息。

### 启动写入窗口补充

`wx` 创建和 PID 写入之间，另一个进程可能看到空文件；POSIX 现在对空或无效 PID 保留原锁并提示确认启动进程后再归档，只有有效 PID 确认 ESRCH 才自动归档。隔离的实际 `acquireLock` 夹具先复现空锁和无效锁被误接管，再验证两者保留、退出码及操作提示；Windows 空锁的既有接管行为维持不变。
